## Остаточные ограничения и порядок ввода

1. Владелец выбирает окружение, выполняет `az login`, затем setup/deploy по [infra/README](../../infra/README.md). Миграции 0003/0004 должны применяться владельцем схемы; старые миграции не переписаны. Их нельзя удалять ради отката приложения. При обновлении со старого JobRunner остановка прежних исполнителей необходима до оценки общего ограничения параллелизма: старая версия ещё не участвует в новом механизме допуска.
2. До пилота подтвердить SP-01/SP-02: consent, права/лицензии, PIM/per-user MFA, Entra/MFA/роли, HSM, доступы и RLS, миграции/swap, KQL на поступивших метриках, доставку оповещений и учебное PITR AT-11. Локальная компиляция Bicep не проверяет запросы и роли в Azure.
3. Принять P1 AT-01…AT-11, назначить ответственных и провести четырёхнедельный пилот 3–5 клиентов; G2 — после фактической приёмки. Подробный порядок — [готовность к пилоту](../dev/pilot-readiness.md).
4. Windows: первый подписанный MSI, SP-04/SP-05, реальные CNG/TPM/DPAPI, обновление/откат, доставка через Atera и проверка её API остаются открытыми. CI Windows smoke пока допускает сбои; ручной выпуск кандидата требует успешных Windows-тестов и отдельного одобрения владельца.
5. Массовое применение политик — отдельная транзакция на клиента, без общей атомарности/автоматического отката. Неизвестный результат подтверждается тем же token. Создание записи библиотеки само по себе не имеет idempotency key: при потере ответа сначала перечитать библиотеку. История шаблонов не очищается автоматически; эти ограничения описаны в [руководстве](../dev/shared-policy-templates.md).
6. Распределённые лимиты требуют одинаковой конфигурации всех экземпляров. KQL, расходы, TLS/DNS и поведение внешних API проверяются при доступе к средам. Исправления этой сессии не являются разрешением на развёртывание или подключение клиентских tenant.
