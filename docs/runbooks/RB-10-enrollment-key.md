# RB-10. Ключ регистрации организации: ротация, утечка, кража ПК

## Назначение

Заменить ключ регистрации организации без перерыва (плановая ротация), отреагировать на его утечку и отозвать устройства, зарегистрированные по утёкшему ключу, или украденный ПК (`04`, «Ключ регистрации организации», угроза R-15). Ключ нужен только для регистрации: уже зарегистрированные агенты работают и после его отзыва.

## Владелец роли и этап

Security Owner (по умолчанию Product Owner; заместитель — Service Manager), этап P2.

## Признак запуска

- Плановая ротация: раз в 12 месяцев, при уходе сотрудника с доступом к секретной переменной RMM, при смене RMM.
- Оповещение «Alert RB-10» (необычно много новых устройств за сутки: больше половины активных, не меньше 10; ключ моложе 14 суток исключён) или новые устройства в сводке Teams, которые не ставили.
- Подозрение на утечку ключа: он найден в журнале RMM, 4688 или 4104, в заявке или чате; ключ показан не тому человеку.
- Кража или потеря ПК с агентом.

## Предусловия и доступы

- Роль Admin в портале с MFA: операции `createEnrollmentKey`, `listEnrollmentKeys`, `revokeEnrollmentKey`, `listDevices`, `revokeDevice`. Admin RMM с правом менять секретные переменные и запускать задания от SYSTEM.
- Активных ключей у организации не больше двух: при двух активных сначала отозвать одну.

## Шаги

### А. Плановая ротация

1. **Создать новый ключ** — `createEnrollmentKey`: «Kunder» → клиент → «Enheter» → «Registreringsnøkler» → «Ny nøkkel» → «Navn» (например, «RMM 2027») → создать. Ключ (`sikk_…`) показывается один раз: «Ny registreringsnøkkel». Копировать прямо в секретную переменную RMM `SIKKERHEIT_ENROLLMENT_KEY` для группы ПК организации; не вставлять в чат, заявку, протокол и скриншоты. Закрыть окно.
2. **Раздать файл ключа на все ПК организации** заданием RMM от SYSTEM (без переустановки MSI):

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File Sikkerheit-Rmm.ps1 -Action SetEnrollmentKey
   ```

   Секретная переменная должна подставляться как **переменная окружения** процесса задания, а не текстом в команду или скрипт (подстановка текста попадает в журнал PowerShell 4104 и в журналы RMM). Скрипт пишет `enrollment.key` в каталог данных (доступен только SYSTEM) и выводит только `result=ok`; служба в течение минуты сохраняет ключ под DPAPI и удаляет файл. ПК, которые выключены, получат файл при следующем запуске задания: настроить повтор. Код выхода ≠ 0 — таблица кодов в [rmm-windows-verification.md](../dev/rmm-windows-verification.md), раздел 1.
3. **Проверить, что новый ключ работает:** ключ в таблице «Registreringsnøkler» имеет «Sist brukt» (после первой новой регистрации) или тестовая регистрация нового ПК проходит.
4. **Отозвать старый ключ** — `revokeEnrollmentKey`: строка старого ключа → «Tilbakekall» → «Tilbakekall nøkkelen». Агенты не затронуты. Старый ключ с этого момента не регистрирует.
5. Удалить старое значение секретной переменной RMM.

### Б. Утечка ключа

1. **Сразу создать новый ключ** (А.1; при двух активных сначала отозвать утёкший — тогда новые ПК временно не регистрируются, это допустимо) и **отозвать утёкший ключ** (А.4). Отзыв прекращает регистрации по нему сразу, зарегистрированные агенты продолжают работу.
2. **Найти, что зарегистрировано по утёкшему ключу** — «Enheter» → фильтр «Registreringsnøkkel» (`listDevices?enrollmentKeyId=…`). Сверить список с ожидаемыми ПК клиента (имена, «Registrert», «Sist sett»). Фильтр доступен Admin.
3. **Посторонние устройства** — строка → «Tilbakekall enheten» (`revokeDevice`, необратимо) для каждого незнакомого ПК. Если Security Owner решил отозвать все устройства по ключу: загрузить все страницы списка, нажать «Tilbakekall enheter for denne nøkkelen», сверить показанный список и подтвердить. Отзыв выполняется по зафиксированному списку, по одному устройству; итог показывает успехи и ID отказов. Неполный список не допускает массовый отзыв. Это не отзывает сам ключ: выполнить Б.1 отдельно. После отзыва устройство не отправляет данные, его проблемы закрываются.
4. **Раздать новый ключ** на ПК, которые ещё не зарегистрированы (А.2), и заменить в RMM секретную переменную.
5. **Источник утечки:** найти и убрать (журнал RMM, заявка, чат). Если ключ был в журнале 4688/4104 — это дефект скрипта или настройки RMM: остановить задания, передать разработчику (скрипт не должен выводить ключ), RB-06 при вероятности чужого доступа к ПК.
6. Проверить, что в сводке Teams и в «Enheter» нет новых неизвестных ПК в ближайшие 24 часа.

### В. Кража или потеря ПК

1. «Enheter» → ПК → «Tilbakekall enheten». Его проблемы закрываются, регистрация этой установки невозможна.
2. Если на ПК мог остаться файл ключа или ключ в DPAPI: ключ защищён DPAPI (LocalMachine) и доступен локальному администратору; поэтому считать ключ скомпрометированным, если ПК не зашифрован BitLocker, и выполнить Б. Для зашифрованного ПК решает Security Owner.
3. Данные клиента на ПК (BitLocker, учётные записи) — вне этого runbook: сообщить клиенту.

## Проверка результата

- «Registreringsnøkler»: утёкший/старый ключ — «Tilbakekalt», новый — «Aktiv»; «Enheter» не содержит посторонних активных устройств по утёкшему ключу.
- На ПК файла `enrollment.key` нет (служба забрала). Ключа нет в журналах: события 4688 (процессы с `msiexec`/`powershell` без `sikk_` в командной строке), 4104 (текст скрипта без значения), Sysmon и журнал заданий RMM — поиск по `sikk_`.
- Новая регистрация нового ПК по новому ключу проходит.
