# RB-13. Ежемесячная сверка каталога выпусков Windows

Владелец — Service Manager с ролью Admin; заместитель назначается до пилота Windows. Выполнять после второго вторника месяца, в течение семи суток, а также после внеочередного выпуска безопасности. До завершения сверки SYS-003 может показывать `unknown`/`release_catalog_stale`; это требует проверки каталога, а не исправления ПК.

## Источники и подготовка

1. Открыть в портале «Windows releases». Записать месяц, дату, ответственного и исходный `verifiedThroughMonth` в протокол по шаблону [README](README.md#протокол).
2. Сверить клиентские ветки Windows по [Windows release health](https://learn.microsoft.com/en-us/windows/release-health/) и страницам истории обновлений Microsoft. Зафиксировать ссылки на конкретные KB и дату выпуска. Серверные ОС не добавлять. Для каждого выпуска нужны `branchBuild`, `ubr`, KB без префикса, фактическая дата, тип, месяц исправлений безопасности и `autoOffered`.
3. Автоматический импорт `msrc_cvrf` создаёт только черновик и не является сверкой. До протокола SP-04 надёжный путь — ручной ввод по первоисточнику. В интерфейсе он выбран по умолчанию.

## Импорт и ввод месяца в действие

1. Выбрать месяц и ручной источник. Одна строка: `build ubr kb kind securityMonth date [auto|manual]`. Дата обязательна и берётся из Microsoft; вычислять её из даты Patch Tuesday нельзя. Для выпуска без исправлений безопасности месяц — `-`. Типы: `security_monthly`, `security_oob`, `nonsecurity_oob`, `preview`, `hotpatch`; для hotpatch проверить применимость к реальным устройствам в SP-04.
2. Нажать импорт. API `importWindowsReleases` создаёт задание; дождаться окончания, заново открыть список и проверить все черновики: сборка, UBR, KB, дата, классификация, автоматическое предложение. Предварительный выпуск без исправлений не должен становиться текущим месяцем безопасности.
3. Сопоставить **все** записи месяца с первоисточником. Затем выполнить `verifyWindowsReleaseMonth`. Если выпусков действительно не было, отметить «нет новых выпусков» после той же проверки; отсутствие данных импорта само по себе не доказывает отсутствие выпусков.
4. Проверить непрерывность сверенных месяцев и обновление `verifiedThroughMonth`. Пропущенный месяц закрыть отдельно. Планировщик поставит `patch_level_sweep` для активных организаций; проверить завершение заданий, оценки SYS-003 и историю событий на лабораторном ПК.
5. После внеочередного выпуска повторить импорт и сверку месяца. Повторная сверка вызывает новый пересчёт. Сверенная запись не перезаписывается импортом: противоречие даёт 422. При ошибке уже сверенной записи остановить дальнейшую сверку, зарегистрировать дефект и исправить его версией сервиса; не менять production-базу вручную.

## Проверка результата и отказ

- В журнале аудита есть операции импорта и сверки с ответственным; ссылки на источники и проверенные ветки приложены к протоколу.
- Месяц сверен, пропусков нет; актуальный ПК не получает ложный fail, отстающий показывает ожидаемый месяц/KB. Сверка без фактов устройства не превращает unknown в pass.
- При сбое импорта сохранить статус задания и correlationId без данных клиентов, проверить RB-04. До подтверждения источника использовать ручной ввод.
- Если обслуживание занимает более 30 минут в месяц или сверка регулярно запаздывает, предложить владельцу перевести SYS-003 в informational до появления надёжного источника; решение оформляется политикой, а не подменой результата.

Реальная сверка и проверка формата MSRC остаются частью SP-04. Наличие этого runbook не означает, что эксперимент пройден.
