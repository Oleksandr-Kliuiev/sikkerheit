# Решения 0.3.0: архитектура под масштаб MSP

Дата: 2026-10-15. Основание — указания пользователя в сессии 2026-10-15:

- проект пишется для небольшой MSP-фирмы: около 40 клиентов и около 400 компьютеров;
- архитектуру 0.2.0 упростить под этот масштаб, закрыв все замечания, противоречия, пробелы и риски;
- разработку ведёт один разработчик с ИИ-агентами;
- клиентские ПК обслуживаются через RMM;
- первым этапом идут проверки Microsoft 365 и Entra, агент Windows — следующим.

Пакет 0.2.0 остаётся замороженным под тегом `package-v0.2.0`. Решения ниже вносятся в версию 0.3.0. Одобрение G0 относилось к 0.2.0 и на 0.3.0 не переносится; гейты 0.3.0 — решения владельца по `docs/WORKFLOW.md`.

## Почему меняется архитектура

0.2.0 рассчитан на SaaS корпоративного уровня. В нём собственный CA и компонент Issuer, mTLS в отдельной среде Container Apps, ротация сертификатов с перекрытиями и окнами повторной регистрации, асинхронная очередь оценки с fencing и откладыванием, внешний версионированный журнал жизненного цикла и restore в девять шагов, RLS с пятью режимами входа. Оценка до пилота — 31–46 инженерных недель на двух инженеров.

При 400 ПК сервер получает около 400 пакетов в сутки. Почти все открытые замечания четвёртого раунда возникли внутри этих механизмов, а не в продуктовой логике:

- сертификаты, Issuer и restore: Fable N4-01 (major), N4-02; Astra N14, N10 и R-16;
- асинхронная очередь и поздние пакеты: Fable N4-03, N4-04; Astra N13;
- история ожидания WIN-006: Astra N12, A01, вопрос 15.

Упрощение убирает эти классы дефектов целиком, а не латает их по одному.

## Решения

| D-01 | Этапы: P0 — подготовка и проверка доступа Graph; P1 — платформа и проверки M365 для всех клиентов; P2 — агент Windows через RMM; P3 — расширения по отдельным решениям | P1 — агент или импорт, P2 — M365 | Указание пользователя «сначала M365»: ценность по всем 40 клиентам без установки ПО |
| D-02 | Один развёртываемый сервис (модульный монолит ASP.NET Core 10): портал, API агента, фоновые задания и сборщик M365 в одном процессе; два hostname — портала и агента | Четыре процесса: Portal API, Agent API, Worker, Issuer; плюс Graph-компонент и компонент импорта | Нагрузка мала; отдельные процессы не окупают эксплуатацию одним человеком |
| D-03 | Хостинг: Azure App Service (Linux), Azure Database for PostgreSQL Flexible Server, Blob Storage, Key Vault, Application Insights; регион Norway East, запасной — Sweden Central | Три среды Container Apps, внутренний VNet для Issuer, два Key Vault | Минимум ресурсов и понятий; данные в Норвегии |
| D-04 | Доступ к M365: одно multi-tenant приложение Entra только с правами чтения; admin consent в каждом клиентском tenant. Закрытый ключ сертификата неэкспортируемый, в Key Vault; client assertion подписывается операцией sign Key Vault | Отдельная регистрация приложения на каждого клиента (ADR-06) | 40 регистраций и 40 сертификатов вручную — слишком дорого для одного человека; ключ не покидает Key Vault |
| D-05 | Устройство агента аутентифицируется своей парой ключей (TPM, иначе неэкспортируемый программный ключ): challenge → подпись → сессионный токен на 60 мин. | D-06 | Регистрация агента — ключом регистрации организации. RMM передаёт его параметром установки; агент хранит ключ под DPAPI машины и сам регистрируется повторно, если сервер не знает устройство | Одноразовые и пакетные enrollment-токены, вопрос «как доставить новый токен установленному агенту» | Закрывает N4-05 и восстановление после restore без участия техника; риск утечки ключа — R-15 |
| D-07 | Агент — одна служба Windows под LocalSystem с фиксированными сборщиками: без дочерних процессов, без входящих портов, без удалённых команд, со строгим разбором ответов | Гипотеза H-02: виртуальная учётная запись плюс privileged collector по named pipe (ADR-02) | Большинству сборщиков нужны права администратора; RMM на тех же ПК уже работает как SYSTEM и умеет выполнять команды, а агент — нет |
| D-08 | Пакет агента принимается и оценивается синхронно, в одной транзакции под блокировкой строки устройства. Пакеты устройства идут строго по sequence; фоновая очередь остаётся только для периодических и запрошенных заданий | Асинхронный `evaluate_batch`, `acceptOrder`, откладывание, поздние пакеты меняют историю | Убирает N4-03, N4-04 и N13; при 400 ПК оценка занимает миллисекунды |
| D-09 | Уровень патчей Windows — серверная проверка SYS-003: build и UBR из WIN-011 сравниваются с каталогом ежемесячных выпусков Windows. WIN-006 становится информационным состоянием службы обновлений | История ожидающих обновлений WUA с эпизодами по источникам, гипотезы H-WU1 и H-WU2 | Убирает N12, A01 и вопрос 15; не требует долгого поиска WUA на ПК |
| D-10 | WIN-007 формулируется как «требование перезагрузки наблюдается во всех сборах с момента T»; непрерывность между сборами не утверждается | «Наблюдается не менее N дней» как нижняя граница | Закрывает A02 |
| D-11 | Все сотрудники MSP видят всех клиентов. Роли — app roles Entra: Admin, Technician, Reader. Назначений по клиентам в P1–P2 нет | PlatformAdmin, ServiceManager, Technician с назначениями и аудитом каждого чтения PlatformAdmin | Решение владельца C-39 уже дало глобальный доступ; в фирме такого размера техники работают со всеми клиентами |
| D-12 | Изоляция клиентов: `organization_id` в каждой клиентской таблице, составные внешние ключи, фильтр области в приложении и простая RLS PostgreSQL. Запись возможна только в области одной организации; чтение всех организаций — только для списков портала | `app.begin_org_context` с пятью `purpose`, роли `app_ctx`, `app_jobs`, перечень исключений | Защищает главные пути (приём данных, отчёты, экспорт) при меньшем объёме кода |
| D-13 | Целостность после restore: ограничивающие действия безопасности (отзыв устройства и ключа регистрации, отключение и удаление организации, отключение M365) пишутся в append-only Blob с политикой неизменяемости до commit. После PITR они воспроизводятся заново | Версионированный `lifecycle_journal`, `decisionVersion`, `journalPendingVersion`, карантин в девять шагов | Тот же итог («restore не возвращает отозванный доступ») без версий; без сертификатов R-16 исчезает |
| D-14 | Отчёт HTML (PDF — печатью из браузера), язык отчёта по организации, портал nb по умолчанию с nn и en | — | Без изменений (решение владельца C-45) |
| D-15 | Ежедневная сводка сотрудникам в канал Teams: новые критические проблемы и сбои сбора | Канал оповещений не выбран | Минимальный канал без писем клиентам; клиентская рассылка остаётся в P3 |
| D-16 | Проверки M365 в P1: регистрация MFA пользователей, MFA администраторов, принуждение к MFA (Security Defaults или CA), блокировка legacy auth (информационно), число глобальных администраторов, согласие пользователей на приложения, неактивные учётные записи (информационно) | M365-001…005 в P2 без контракта | Самые ценные для MSP проверки и минимальный набор прав чтения |
| D-17 | Регистрация MFA читается по методам аутентификации каждого пользователя (`/users/{id}/authentication/methods`) — одинаково в tenant с Entra ID P1 и без него; лицензия определяется по `subscribedSkus` | Отчёт `userRegistrationDetails` (требует P1) | Многие небольшие клиенты на Business Standard без P1 |
| D-18 | Агент поддерживает Windows 11 и Windows 10 22H2 x64; на Windows 10 SYS-002 даёт fail, оплаченный ESU оформляется решением о риске со сроком пересмотра | Только Windows 11 Pro 25H2 и 26H2 | Windows 10 у клиентов MSP — главный риск, его нужно видеть |
| D-19 | Импорт фактов из RMM и Intune вместо агента в P1–P2 не делается: RMM — канал установки агента, Intune — кандидат P3 | Gate SP-05 с вариантами A и B | Пользователь выбрал агент через RMM; семантика проверок у разных RMM разная |

После внесения правок ещё один субагент Claude ([отчёт аудита](../reports/2026-10-15-audit-review-fixes.md)) проверил, закрыты ли RV-01…RV-35, и пересчитал арифметику (HMAC-вектор, 22 значения `servicingEndsAt`, расходы, календарь, отсутствие unknown SYS-003 при сверке через 1–13 суток). Он нашёл 24 остатка и новых несогласованности, все исправлены:

- время отправки пакета вынесено из тела в заголовок `Sikkerheit-Sent-At`: иначе повтор после backoff получал признак часов или терял идемпотентность;
- у планов Basic нет слотов, поэтому для test и запасного варианта B2 описана процедура миграций без слота;
- учебное восстановление не трогает файлы production, а реальное переносит файлы без строк в карантин на 30 суток вместо удаления;
- добавлена сущность `device_presence` для знаменателя покрытия Windows и NFR-02;
- оповещение о точном клоне — по повторяемости resync, а не по числу за сутки;
- в Unenrolled агент регистрируется сразу при входе в состояние и при появлении файла ключа;
- вход SYS-002/003 и `lastAcceptedCompletedAt` берутся только из пакетов, способных менять проекцию;
- пакет с номером потерянной ревизии получает `unknown_policy_version`;
- действия `drop_batch`, `refresh_configuration`, `resync_sequence` и `renew_session` не меняют состояние агента;
- внеплановый `patch_level_sweep` получает ключ месяца, импорт каталога — задание `release_import`;
- вывод устройства из учёта через 90 суток выполняет `freshness_sweep`;
- уточнены роли Admin, перечень чтения всех организаций, определение `source_change` для SYS-*, формулировка о незакоммиченной отмене удаления, `ReleaseId` у сборок до 20H2, назначение ключа регистрации, недоверенные строки и метрики телеметрии для RB-08 и RB-12;
- ориентиры календаря явно привязаны к месту праздников и отпуска.

Риски и допущения ревью без дефекта текста (H-KEY и сброс fTPM, `graceDays` и отсрочка RMM, `IAutomaticUpdatesResults` при USO, распространённость hotpatch, сертификаты Secure Boot 2011) перенесены в SP-04, R-08, вопросы 3 и 16 и кандидаты P3.

### Не сделано и риски

- Правила Azure Monitor по метрикам агента (`infra/bicep`): сигналы есть в метриках и журнале, но оповещения не заведены.
- Редактор параметров WIN и SYS в политике портала: параметры действуют через API, форма — не в этом проходе (на странице политики это сказано).
- Ограничитель частоты — в памяти экземпляра; при слотах и нескольких экземплярах лимиты приблизительные.
- Источник каталога (MSRC CVRF) и формат импорта не проверены на реальных данных; пока SP-04 не выбрал источник, надёжный путь — ручной ввод.
- Эксплуатационные расчёты: нагрузка `submitScan` (NFR-04) не измерялась; блокировка строки устройства сериализует пакеты одного ПК, но не разных.
