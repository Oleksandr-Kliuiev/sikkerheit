# Atera: локальная сверка инвентаря

Владелец выбрал Atera для RMM/PSA. `tools/atera/check_inventory.py` читает нормализованные локальные снимки Atera и Sikkerheit, проверяет явные связи клиентов и устройств, формирует JSON-отчёт. Сетевых запросов, установки агента, отзыва устройств и создания заявок нет. Ключ API не нужен.

## Возможности

Сверяются неподтверждённые связи в обоих направлениях, отсутствие ранее связанного ID в полном свежем снимке, отзыв, конфликт идентичности, старый контакт и версия ниже явно переданного минимума. Проверяются полнота страниц и свежесть источников.

Совпавшие имена — только кандидаты внутри связанной организации. Они не устанавливают идентичность: `PC-01` может существовать у разных клиентов. Старый контакт Sikkerheit не доказывает, что ПК был онлайн по RMM; это отмечается в результате.

## Вход

Пример с вымышленными данными — `tools/atera/examples/pilot-snapshot.json`. Это формат инструмента, не предполагаемая схема ответа Atera API.

| Поле | Содержание |
| --- | --- |
| `schemaVersion` | Целое `1` |
| `atera.capturedAt`, `sikkerheit.capturedAt` | Время снимка ISO с timezone |
| `atera.complete`, `sikkerheit.complete` | Явное подтверждение полноты в выбранной области |
| `atera.agents` | Нормализованные `agentId`, `customerId`, `name` |
| `sikkerheit.organizations` | `organizationId` и `pages` с ответами `listDevices` |
| `pages[].cursor` | Курсор запроса; первая страница — `null` |
| `pages[].items`, `pages[].nextCursor` | Данные `DevicePage`; последняя страница — `nextCursor=null` |
| `customerMappings` | Подтверждённые `customerId` → `organizationId`, один к одному |
| `deviceMappings` | Подтверждённые `agentId`, `organizationId`, `deviceId`, один к одному |

Не подтверждать полноту, если выгрузка ограничена страницей или фильтром, исключающим устройства выбранных клиентов. Неверная цепочка страниц, повторные ID и связь через границу клиента отклоняются. Неизвестные поля источников не копируются в отчёт.

## Запуск

Из корня репозитория, без доступов:

```bash
python3 -I tools/atera/check_inventory.py \
  --input tools/atera/examples/pilot-snapshot.json \
  --report .dev/scaling/atera-example-report.json \
  --as-of 2026-10-17T12:00:00Z \
  --minimum-agent-version 0.1.0
```

Для реальных снимков убрать `--as-of`: используется текущее UTC-время. По умолчанию свежесть снимка — до 24 часов, старый контакт — более 48 часов. Параметры: `--snapshot-max-age-hours`, `--stale-hours`. Версии сравниваются численно; без минимальной версии эта проверка не выполняется.

Коды завершения: `0` — сравнение полных свежих снимков выполнено, даже при найденных расхождениях; `2` — полнота или свежесть не подтверждена; `1` — ошибочный вход или запись. `comparisonComplete` означает достаточность снимков, а не исправность устройств или покрытие проверок.

Отчёт содержит область клиентов, время источников, сводку и `issues`. `unlinked_agent`/`unlinked_device` требуют проверки связи. `mapped_device_missing` и `mapped_atera_agent_missing` требуют достаточного снимка источника; `coverage_unconfirmed` не объявляет устройство отсутствующим. `last_seen_old` не подтверждает онлайн-присутствие по RMM.

Отчёт может содержать имена ПК и ID клиентов. В macOS/Linux файл имеет права `0600`; `.dev/` исключён из git. В Windows использовать каталог с доступом ответственных сотрудников. Вход не перезаписывается, максимальный размер — 10 MiB.

## Следующий этап API

[Atera описывает](https://support.atera.com/hc/en-us/articles/219083397-Using-the-Atera-API) домены Agents и Customers и токены с ограничением по IP, сроком и Custom access по доменам. Для инвентаря нужны только чтения этих доменов. Ключ не передавать в чат, Git или аргументы команд.

Актуальная документация методов `app.atera.com/apidocs` требует входа: публичное чтение вернуло 401. Поэтому транспорт, пагинация, лимиты и поля онлайн-присутствия не угадываются. После доступа сверить схему API и нормализацию на одном тестовом клиенте, затем подключать чтение к уже проверенной сверке.

Запись заявок требует отдельной части: минимальные права Tickets, подтверждённое соответствие клиентов, устойчивая ссылка на finding, защита от дублей и сверка неопределённого результата отправки. Закрытие заявки Atera не должно само закрывать техническое отклонение: устранение подтверждает повторная проверка источника. Настоящие API-чтения и запись заявок здесь не проверялись.
