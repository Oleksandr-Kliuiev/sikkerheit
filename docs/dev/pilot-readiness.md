# Подготовка пилота: состояние и следующие действия

Состояние после итогового ревью и сборки 0.3.2, 2026-10-17. **Готово к развёртыванию и квалификационным проверкам на тестовой среде; реальный пилот ещё не допущен.** Код проверен локально; **G1, G2, допуск пилота Windows и G3 не пройдены**. Владелец сообщил, что доступы к Azure, tenant, Windows и RMM предоставит позже. Эта запись не заменяет протоколы экспериментов и приёмку человеком.

## Закрытые расхождения кода и развёртывания

| Расхождение | Изменение | Проверка |
| --- | --- | --- |
| Production требует `Agents:NonceKey`, setup и Bicep его не задавали | `agents-nonce-key` в Key Vault, ссылка обоим слотам; существующий ключ не заменяется при ошибке чтения | IaC, негативные варианты, офлайн-тесты setup, реальный bootstrap с синтетическими настройками |
| Без `Hosting:AgentHosts` API агента принимал любой hostname | Явный hostname; `disabled.invalid` закрывает P2 для первого выпуска M365; у staging отдельное правило для smoke | IaC, HTTP-тесты разделения hostname |
| Минимальная версия могла сброситься при setup или swap | Setup сохраняет live hostname и minimum version; параметры закреплены за слотами | Тест повторного setup и негативная проверка sticky settings |
| Linux App Service не передавал приложению исходный IP/HTTPS | Включён стандартный forwarded-headers режим ASP.NET Core для единственного ingress App Service | Проверка ARM; реальную цепочку proxy/IP подтверждает SP-02/SP-05 |
| Deployment не проверял API агента и результат после swap | Challenge `purpose=enroll`, 201 при включённом P2; иначе 404; разделение hostname; smoke после swap | Настоящий HTTP API в интеграционном тесте, отказ smoke вызывает cleanup |
| Не было отдельной проверки Production-bootstrap | Список обязательных настроек сверяется с ARM; ключи проверяются на base64/32 байта; команда `check-configuration` | Три запуска bootstrap: M365, Windows, staging, без внешних запросов |
| Не было отдельных Azure Monitor правил P2 | Пять правил: ошибки агента, перезапуски, память, отклонённые пакеты, скорость/5xx приёма | Bicep, IaC, имена метрик сверяются с исходниками; KQL и доставку письма подтвердить в SP-05 |

Закрыты и локальные недоделки: редактор параметров WIN/SYS и расписания агента, фильтр и подтверждённый отзыв устройств по ключу, RB-13. Ручной импорт каталога больше не придумывает дату выпуска; дата обязательна. Подготовлен ручной workflow `agent-release`: подпись файлов → MSI → подпись MSI → проверка издателя, отметки времени, версии и SHA-256. **На Windows он ещё не выполнялся.**

## Что готово и что ограничивает допуск

| Область | Локально подтверждено | Для допуска требуется |
| --- | --- | --- |
| P1 Microsoft 365 | Сервис, портал, отчёты, задачи, библиотека политик; тесты ролей, RLS, повторов, Graph и очереди | SP-01 с consent и лицензиями; SP-02 с Entra/MFA, HSM, доступами, staging и восстановлением |
| Обновление с 0.3.1 | Новые миграции 0003 (квоты Graph) и 0004 (библиотека и квитанции), прежние SQL-миграции сохранены | Миграции владельцем схемы в staging, smoke до/после swap; старые слоты остановлены |
| Эксплуатация | Скрипты, runbooks, синтетические оповещения и метрики, нагрузочный профиль PostgreSQL | Проверить KQL на поступившей телеметрии, получение оповещений, AT-11/PITR и фактические ресурсы Azure |
| Windows / Atera | Код агента, сервер P2, редактор, RMM-скрипт, конвейер кандидата, офлайн-сверка снимков | Windows SP-04/SP-05, подписанный MSI, подтверждение Atera API и реальной доставки через RMM |

Без этих сред невозможно подтвердить работоспособность внешних интеграций. Готовность не выражается одним процентом: код и комплект готовы к проверкам, а облачные и Windows-критерии приёмки остаются открытыми.

## Последовательность до пилота M365

1. Владелец выбирает `test`/`prod`, почтовый адрес оповещений и подтверждает расходы. Вход в своём терминале — `az login`; секреты не передавать через чат. До развёртывания согласовать конкретное окружение и изменения.
2. Выполнить `infra/scripts/setup.sh <env>`, затем `deploy-app.sh <env>` по [infra/README](../../infra/README.md). Для первого M365-выпуска агент остаётся закрытым; отдельный домен ему пока не нужен.
3. Пройти **SP-02**: Entra/MFA и прекращение сессий, managed identity и RLS, HSM-подпись, неизменяемость журнала, staging/migrations/swap, задания и оповещения. Провести настоящее учебное восстановление `drill.sh`, измерить RTO и оформить AT-11. Локальная копия базы не доказывает работоспособность PITR Azure.
4. Пройти **SP-01** на tenant компании и двух пробных tenant Business Premium/Business Standard. Зафиксировать endpoint, право, лицензию, фактический ответ, время и контрольные входы MFA. Клиентские tenant — после договоров обработки данных. Проверить обоими путями consent, отзыв consent, PIM, неполные данные, лицензии и эталонный отрицательный случай report-only.
5. Принять части P1 **AT-01…AT-11**, тексты nb/nn/en и примеры отчётов. Настроить Workflows Teams, роли сотрудников и Conditional Access, подтверждение издателя Graph Reader. Назначить Security Owner, заместителя и владельцев RB-01…RB-07/RB-14.
6. Владелец фиксирует **G1** и выбранных 3–5 клиентов. Запустить четырёхнедельный пилот; еженедельно записывать доставку, unknown, ложные pass/fail, понятность отчёта, время техников и затраты. Условия продолжения — `01`, «Экономика пилотов». По итогам исправлений и приёмки AT-17 — G2 и подключение остальных клиентов.

## Подготовка Windows параллельно с пилотом M365

1. **SP-04:** [Windows-лаборатория](agent-windows-verification.md), LocalSystem, реальные CNG/TPM и DPAPI, WMI/COM, Defender и сторонние продукты, клоны, семь суток офлайн, время/ресурсы, прокси и настоящий сервер. Уточнить источники и классификацию MSRC, затем выполнить RB-13 на реальных выпусках.
2. Подготовить DNS/TLS: `infra/scripts/configure-agent-host.sh <env> agent.example.no --plan` показывает CNAME/TXT. После настройки DNS оператор отдельно выполняет `--apply`, затем setup с `SIKKERHEIT_AGENT_HOST=agent.example.no`. Скрипт привязки TLS сам API агента не включает.
3. В GitHub создать защищённое окружение `agent-release`: Required reviewers, ветка `main`; отдельная OIDC identity с правом подписи только нужного certificate profile. Переменные: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `SIGNING_ENDPOINT`, `SIGNING_ACCOUNT`, `SIGNING_PROFILE`, `PUBLISHER_COMMON_NAME`, `PUBLISHER_ORGANIZATION`.
4. Владелец завершает проверку организации Artifact Signing и решает вопрос лицензии WiX v7. Только после этого вручную запускает workflow `agent-release` с подтверждением EULA/условий, версией, издателем и HTTPS origin агента. Этот workflow создаёт **кандидат**, не публикует его в RMM или на клиентские ПК. Версия WiX/Util закреплена — 7.0.0; смена версии требует проверки сборки.
5. **SP-05:** [проверка распространения](rmm-windows-verification.md), первый подписанный MSI, установка/обновление/понижение с сохранением идентичности и буфера, неудачное обновление и удаление; секрет через окружение RMM, а не подстановка текста. Проверить все выходы RMM и отсутствие ключей в 4688/4104/журналах.
6. На настоящем Application Insights подтвердить таблицы/поля KQL и все пять оповещений, экспорт метрик, адресата письма, пороги и остановку кольца. Пройти остальные части P2 приёмки, включая совместимость N−1/N+1 и нагрузку на целевой масштаб. Назначить владельцев RB-08…RB-13.
7. После допуска — пилот 20–40 ПК у 3–5 клиентов на шесть недель, исправления и G3. Раскатка — только по кольцам RB-08 с наблюдением и проверенным откатом.

## Как вести доказательства

Итоговый протокол — [ревью 0.3.2](../reports/2026-10-17-release-0.3.2-review.md): Release без ошибок/предупреждений, .NET 602 успешных и 5 ожидаемых пропусков (607 всего), портал 54 теста и typecheck/lint/build, IaC 50 проверок и 62 отвергнутых испорченных варианта, Azure-скрипты 44 офлайн-теста, Atera 15, RMM 31, валидатор MSI 4. Отдельно проверены Production-bootstrap и профиль очереди на 1100 синтетических заданий. Стандартная проверка пакета выполнена jsonschema 4.26.0 и openapi-spec-validator 0.9.0; ZIP и manifest проверены. Пропуски — четыре Windows smoke и профиль нагрузки, который выполняется отдельным запуском. CI на GitHub и Windows release-workflow в этой работе не запускались.

Протоколы SP-01/SP-02/SP-04/SP-05: дата, версии и окружение, процедура, сырые обезличенные замеры, результат каждого критерия, дефекты, остаточный риск и подпись ответственного (`07`, «Правила этапов и гейты»). Сценарий, проверенный на заглушке, не отмечается как прошедший в Azure/Windows. Данные клиентов, ключи, токены и ссылки SAS не сохранять в Git.

Пакет 0.3.2 собран по указанию владельца; SHA-256 — в [WORKFLOW](../WORKFLOW.md). Создан локальный аннотированный тег `package-v0.3.2` на коммите `2a16cb5`; облачное развёртывание не выполнялось. Пакет содержит документы и контракты, не MSI и не исполняемый сервис. P3 остаётся вне утверждённого объёма: каждое расширение требует отдельного решения.

- [Azure Artifact Signing Action](https://github.com/Azure/artifact-signing-action): OIDC, подпись файлов до упаковки, RFC3161 timestamp.
- [WiX: явное принятие EULA](https://docs.firegiant.com/wix/osmf/). Условия принимает владелец при ручном запуске, а не агент в этой сессии.
